# 재고 차감 처리량 벤치마크: Redis Lua vs RDB(조건부 UPDATE)

같은 워크로드(단일 인기 상품 하나에 여러 스레드가 동시에 재고를 1씩 차감)를
양쪽 저장소에 흘려 "차감 메커니즘 자체"의 처리량만 격리해 비교한다.
Kafka·네트워크가 끼는 k6 end-to-end와 달리 차감 원자성의 비용만 측정한다.

## 실행

```bash
./gradlew :inventory-service:test --tests "*InventoryStoreBenchmarkTest*" \
  -Dbenchmark.ops=5000 -Dbenchmark.threads=30
```

- 양쪽 저장소(Redis 7, MySQL 8)는 Testcontainers가 자동 기동
- 규모는 `-Dbenchmark.ops`, `-Dbenchmark.threads`로 조절
- 정확성(모든 차감 성공 + 재고 정확히 0)만 assert, 처리량은 로그로 출력

## 측정 결과 (로컬, 5000건 / 30스레드 / 단일 상품 경합)

```
===== 재고 차감 처리량 비교 (ops=5000, threads=30, 단일 상품 경합) =====
Redis Lua   : 2417 ms  (2069 ops/sec)
RDB  UPDATE : 31152 ms  (161 ops/sec)
Redis가 RDB 대비 약 12.9배 빠름
==============================================================
```

## 해석

- **Redis Lua (2069 ops/sec)**: 단일 스레드가 `GET+DECRBY`를 원자 실행. 인메모리 + 락 경합 없음.
- **RDB UPDATE (161 ops/sec)**: 단일 행에 몰리니 InnoDB가 행 락으로 5000 트랜잭션을 전부
  **직렬화**하고, 각 커밋마다 **fsync**(내구성 보장)로 디스크 동기화. 이 둘이 처리량을 지배한다.
- 즉 이 격차는 "경합 최악 + 내구성 보장"의 대가다. 상품이 여러 개로 분산되면(경합↓)
  RDB도 서로 다른 행을 병렬 처리해 격차가 줄어든다.

## 트레이드오프 (속도가 전부가 아니다)

| | Redis Lua | RDB UPDATE |
|---|---|---|
| 처리량(경합 시) | 빠름 | 느림 (직렬화 + fsync) |
| 내구성 | 별도 영속화 설정 필요 | 커밋 = 영속 (기본) |
| 트랜잭션 결합 | 타 비즈니스 쓰기와 못 묶음 | 같은 트랜잭션에 묶임 |
| 조회성 | 카운터만 | JOIN·리포팅 가능 |
| 운영 | 저장소 추가 | 기존 RDB로 통합 |

> 주의: 절대 수치는 머신·설정에 따라 달라진다. 의미 있는 건 배율과 "왜 이렇게 갈리는가"이다.
